# **プロダクト要件定義書（PRD）：オーディション採点アプリ**

# **1\. プロダクト概要（Overview & Context）**

## **1.1. 背景と手動運用の課題**

* 現在、サークル内オーディションにおいてGoogleフォーム、スプレッドシート、Excelを組み合わせた手動運用を行っている。  
* 所属部員約100名、エントリー最大32バンド規模のイベントにおいて、データ転記や関数操作に伴うヒューマンエラー（集計ミス）のリスクが高頻度で発生しているため、集計・転記プロセス自体の完全自動化が強く求められている。  
* 自バンド（自身が出演・所属するバンド）に対する採点の混入防止チェックが手動であり、不正や計算・除外漏れが生じやすい。

## **1.2. 目的・ビジョン**

* 採点入力からペナルティ減点・自バンド自動除外・リアルタイム自動集計までをWebアプリ上で一元化し、集計ミスゼロおよび運用工数90%削減を目指す。  
* 透明性・信頼性の高い集計アルゴリズムとCSV/Excel形式でのデータ出力機能を提供し、公平な評価環境を提供する。

# **2\. プロジェクトの境界線（Goals, Non-Goals, Nice-to-have）**

## **2.1. Goals（必須達成目標）**

* **大規模同時入力と永続化：**最大32バンド・100人規模の同時採点に対応するWebフォームおよびデータ永続化の実装。  
* **認証と部員権限判定：**Googleログイン（学内ドメイン限定）による認証と、部員マスタに基づく自動権限判定。  
* **自バンド自動除外：**自分が所属するバンドに対する採点の自動除外処理（自バンドの非表示/ロック）。  
* **リアルタイム採点・合計表示：**採点時における「技術点・魅力点（0〜50）」の入力と、合計点のリアルタイム表示。  
* **提出ステータス管理：**採点・コメント提出完了状況の管理画面からの確認（未提出者の把握）。  
* **ペナルティ管理機能：**オーディション単位でのペナルティ機能の有効/無効切替（is\_penalty\_enabled）および、管理者によるバンドごとのペナルティ減点（penalty\_deduction）の手動設定と自動引き算処理。  
* **出演バンド登録・共同編集機能：**バンド募集中（`DRAFT`）における、ログイン済みの全部員による出演バンド新規登録および共同編集機能（部員マスタからのメンバー選択による表記揺れ防止、および募集締切・調整中（`ENTRY_CLOSED`）以降での自動ロック機能を含む）。  
* **データエクスポート・運用設定：**集計結果および詳細 Raw データの CSV/Excel エクスポート、ペナルティ制度の切替など、コード改修なしで管理画面から全運用設定を完了可能とする。

## **2.2. Non-Goals（非対応・スコープ外）**

* **メディア配信：**オーディション当日の動画・音源ストリーミング配信機能。  
* **外部システム連携：**サークル会費決済・外部会計システムとの連動機能。  
* **高度なグラフ描画：**アプリ内での動的な複雑なグラフ描画（集計とCSV出力で代替）。  
* **手動スコアオーバーライド：**管理者による最終スコア・順位の直接手動オーバーライド機能（代理入力・個別補正は運用マスタ等で対応）。

## **2.3. Nice-to-have（将来的な拡張案）**

* **高度な集計アルゴリズム：**Z スコア（標準化スコア）の導入、および管理画面ダッシュボード上での集計アルゴリズム（Zスコア方式・従来の点差補正方式・単純平均など）のワンクリック切り替え・比較ビュー機能。  
* **コメントシート自動生成：**各バンドごとの評価・コメントを自動整形したコメントシートの自動生成機能。  
* **下書き保存機能：**localStorage を活用した入力途中の下書き自動保存・復元機能。  
* **リマインド通知機能：**締め切り自動リマインド通知機能（Cloudflare Workers の Cron Triggers を活用した未提出者への自動リマインドメール送信）。  
* **スマホ誤操作防止ロック：**スマートフォンのスクロールやタッチミスによる数値の意図しない変更を防ぐため、入力完了したバンドごとに「ロック（確定）」状態に切り替えられる機能。  
* **詳細生データエクスポート：**透明性確保と検算のため、全投票の素点および計算途中のスコアをワンクリックでExcel/CSV出力する機能。

# **3\. 対象ユーザーと利用シーン（Target Users & User Stories）**

## **3.1. ターゲットユーザー区分**

* **一般部員（採点者）**：オーディション参加・鑑賞中にスマホからリアルタイム採点を行う、或いはオーディション動画を閲覧中にスマホから採点を入力する、約100名のユーザー。  
* **渉外・委員（管理者）**：オーディション作成、バンド登録、ペナルティ入力、集計・順位確定を行う管理ユーザー。

## **3.2. ユーザーストーリー**

* 採点者として、自分が所属するバンドの演奏時には自バンド選択の手間や誤採点を意識することなく、システム側で安全に自動スキップ/無効化処理を行ってほしい。技術点と魅力点の合計の計算をシステムに任せたい。  
* 運営者として、100名の採点データやペナルティ減点が即座に自動反映された正確なランキングを確認したい。誰が採点を出していないかをすぐに把握したい。採点者の技術点と魅力点の合計点が合っているか確認する手間をなくしたい。とにかく手作業を減らしたい。

# **4\. 機能要件（Functional Requirements）**

## **4.1. 認証・ユーザー管理**

* サークル部員認証（大学のGsuiteアカウントによるOAuth）。  
* 所属バンド紐付け管理機能（部員ごとに所属するバンドを事前設定）。  
* **スーパーユーザー自動設定（ブートストラップ）**：環境変数 `INITIAL_ADMIN_EMAILS` に指定されたメールアドレスでログインしたユーザーは、初回ログイン時に自動的に ADMIN ロールとして登録。それ以外の一般ユーザーはデフォルトで VOTER ロールとして作成。  
* **部員権限管理（ADMIN/VOTER切替）**：管理者画面から任意の部員のロール（ADMIN / VOTER）を即座に変更・更新できる機能。  
* **ローカル開発用ダミーログイン**：ローカル開発・検証環境において、Google OAuth 設定なしでも任意の検証用部員アカウント（ADMIN / VOTER / COMMENT_ONLY 等）としてログインできるモック認証切替機能を提供。

## **4.2. 採点フォーム・入力機能**

* 魅力点50・技術点50（各項目スライダーまたは数値入力）および定性コメント入力。  
  * 魅力点と技術点の合計を常に確認できるUI  
  * 参加権限（AuditionVoters）に応じた動的バリデーション：  
    * **SCORE\_AND\_COMMENT**：技術点・魅力点・コメントのすべてを入力必須とする。  
    * **COMMENT\_ONLY**：点数入力欄を非表示（または入力不可）にし、全対象バンド分のコメント入力のみを必須とする。  
  * ACTIVEなオーディションのAuditionVotersに未登録のユーザーには専用案内画面を表示。  
* **自バンド投票排除ロジック**：ログインユーザーがメンバーとして登録されているバンドの採点画面では入力フィールドを非活性（または「自バンドのため採点対象外」表示）とし、集計母数から自動除外。  
* 最後に自分がつけたバンドの点数・コメントと順位を確認可能。

## **4.3. ペナルティ管理・自動集計機能**

* **オーディション単位のペナルティ機能トグル（is\_penalty\_enabled）**：オーディションごとにペナルティ減点機能の有効/無効を柔軟に切り替え可能とする。  
* **バンドごとのペナルティ減点設定（penalty\_deduction）**：管理者（ADMIN）が開催回・バンド単位でミーティング遅刻・欠席等に伴う減点（例: 100点満点換算・偏差値換算の直感的な減点数値）を手動で設定し、システムが集計結果に適切に縮尺・反映する。  
* **点差補正方式（審査員の甘辛補正）による正規化・集計ロジックの採用**：審査員ごとの付け方の偏り（甘辛のばらつき）を平準化するため、以下の手順で自動計算を行いリアルタイムで総合順位を算出する。**※現行通りのまま一旦実装する。今後はZスコアに変更すべき。**  
  * **1\. 審査員ごとの基準値算出**：各審査員がつけた全体の「最高点（MAX）」と「最低点（MIN）」、および「点差（Diff \= MAX \- MIN）」を算出。  
  * **2\. 補正係数の適用**：審査員ごとの点差に基づき、基準定数 `10` を用いた補正係数（`10 / Diff`、ただし `Diff = 0` または有効採点1件以下時は `1.0`）を算出（管理画面から定数変更およびZスコア方式・単純平均方式への切り替え・比較も可能）。  
  * **3\. 個別得点の正規化・技術魅力按分**：各バンドに対する素点合計に補正係数を乗算し、正規化された合計得点を算出。また、正規化後の技術点・魅力点については、元の素点における技術点・魅力点の割合をもとに合計点の正規化後点数から按分算出する（素点合計が0の場合は均等割）。  
  * **4\. 補正後平均・総合順位算出**：有効投票（自バンド・未入力除外）における正規化得点/Zスコアの平均を求め、ペナルティ有効時は最終スコアからバンドごとのペナルティ減点を差し引いて最終ランキングを算出。  
* tech\_score / charm\_score が NULL のレコードは集計計算（平均点・Zスコア等）から自動除外（CSV/Excel出力の講評コメント一覧には出力対象として含める）。  
* **ペナルティ減点の非破壊集計**：バンドごとの penalty\_deduction は生データ（Scores の tech\_score / charm\_score）および正規化/Zスコア計算自体には影響を与えず保持し、すべての正規化・標準化計算が完了した後の最終集計スコアに対してのみ非破壊的に差し引いてランキングおよびCSVを出力する。

## **4.4. エクスポート機能**

* 集計結果・各採点者のRawデータおよびバンド別講評をCSVおよびExcel (xlsx) 形式で一括ダウンロード（用途別に以下の2ファイルを用意）。  
  * **ファイル1（集計結果・生データブック）**：①「総合ランキング集計シート」と、②「全採点Rawデータ＆補正計算過程シート」の2シート構成。  
  * **ファイル2（バンド別講評コメントブック）**：各バンドごとに個別シートを作成し、各シートに採点者の対象バンドに対する正規化後点数（魅力点・技術点・合計点）およびコメントを掲載（素点比例按分による正規化魅力・技術点を表示し、コメントのみ権限等は点数欄をハイフン表示）。  
* **未提出者の確認・モニタリング機能**：管理画面のダッシュボードにて、開催回ごとの提出対象者（AuditionVoters）のうち、期限までに採点・コメントの提出が完了していない「未提出者」を一覧表示し、ステータス別に確認できる機能。

## **4.5. オーディション開催回管理機能（管理者権限）**

* **新規オーディション作成**：イベント名を指定して「バンド募集中（`DRAFT`）」状態で新規作成できる機能。  
* **マスタ一括登録**：対象オーディション（audition\_id）に紐づく参加バンド・出演順・メンバーをCSVまたはテキスト貼り付けで一括登録できる機能。  
* **参加者権限の一括設定**：条件（入部年度/回生や出演有無等）に応じた参加権限（SCORE\_AND\_COMMENT / COMMENT\_ONLY）の一括付与・解除機能。  
* **バンド登録・共同編集機能**：オーディションのステータスが「バンド募集中（`DRAFT`）」の期間中、ログイン済みの全ユーザー（VOTER / ADMIN）が出演バンドの新規追加および既存バンド情報の編集・メンバー変更を行える機能。メンバー登録は部員マスタ（Users）からの検索・選択方式とし、表記揺れを防ぐ。また監査のため最終更新者（updated\_by）を記録する。  
* **進行ステータス切替（4段階）**：管理画面からステータスを「バンド募集中（`DRAFT`）」→「募集締切・調整中（`ENTRY_CLOSED`）」→「採点受付中（`ACTIVE`）」→「採点終了・集計（`CLOSED`）」に切り替えられる機能。採点受付中に切り替えた際、既存の採点受付中のオーディションは自動的に採点終了・集計になり、一般部員の採点画面には常に採点受付中のオーディションのみが表示される。

# **5\. 非機能要件（Non-Functional Requirements）**

* **性能・応答性**：100ユーザーからの同時リクエストにおいて、採点送信レスポンス1秒以内。  
* **可用性・信頼性**：オーディション開催中のシステム稼働率99.9%を保証。二重送信防止ロック機能。採点内容の編集は可能にする。  
* **セキュリティ**：Role-Based Access Control (RBAC) による一般部員と運営管理者の権限分離。

# **6\. データモデル・スキーマ（Data Schema & Architecture）**

## **6.1. エンティティ構成**

* **Users** (id, name, email, role\[ADMIN\|VOTER / デフォルト: VOTER\], enrollment\_year) ※ grade（回生）の代わりに enrollment\_year（入部年度: 例 2024）を保持し、現在の西暦から動的に回生を算出する。 ※初回認証時、環境変数 INITIAL\_ADMIN\_EMAILS に含まれるアドレスは ADMIN で初期生成  
* **Bands** (id, audition\_id, name, performance\_order, penalty\_deduction, updated\_by\_user\_id, updated\_at)  
* **Scores** (id, audition\_id, band\_id, evaluator\_user\_id, tech\_score\[NULL可\], charm\_score\[NULL可\], comment, created\_at) ※(audition\_id, band\_id, evaluator\_user\_id) の複合ユニーク制約により二重送信を防止  
* **Auditions** (id, title, event\_date, deadline\[DATETIME\], status\[DRAFT\|ENTRY\_CLOSED\|ACTIVE\|CLOSED\], is\_penalty\_enabled, created\_at)  
* **AuditionVoters** (id, audition\_id, user\_id, permission\_type\[SCORE\_AND\_COMMENT\|COMMENT\_ONLY\]) ※(audition\_id, user\_id) の複合ユニーク制約

# **7\. システム構成・技術スタック（Tech Stack）**

* **フロントエンド:** React (Vite), TypeScript, Tailwind CSS, React Hook Form, Zod  
* **バックエンド / API:** Hono（Cloudflare Workers 上で `/api/*` を処理、Hono RPC で型共有）  
* **認証:** Google OAuth 2.0（`@hono/oauth-providers` ＋ ドメイン制限 ＋ HTTPOnly Cookie セッション）  
* **データベース / ORM:** Cloudflare D1 (SQLite) / Drizzle ORM  
* **ホスティング:** Cloudflare Workers（Workers Static Assets でフロントとAPIを単一デプロイ）

# **8\. 画面仕様・UIフロー（Screen Flow）**

* **ログイン画面**：部員認証・アカウント作成。  
* **バンド一覧・タイムテーブル画面**：演奏順の確認と各バンドの採点ステータス表示。  
* **採点入力画面**：魅力点・技術点・コメント入力（自バンドの場合は「無効化表示」）。  
* **バンド登録・一覧画面**：オーディションのステータスが「バンド募集中（`DRAFT`）」の間、ログイン済みの全部員（VOTER / ADMIN）が閲覧・新規登録・編集できる画面。メンバー選択は部員マスタ（Users）からの検索・複数選択UIとし、最終更新者（updated\_by）を画面上に表示する。ステータスが「募集締切・調整中（`ENTRY_CLOSED`）」以降は一般部員に対して自動ロック（閲覧のみ）となる。  
* **【運営】管理ダッシュボード**：ペナルティ設定、リアルタイム集計ランキング、CSV/Excel出力。  
* **【運営】オーディション新規作成・初期設定画面**：開催回名（例：2026 冬ライブオーディション）および開催日（event\_date）の入力、参加バンド・出演順・メンバーの一括登録、および採点・コメント提出対象者の権限（採点＋コメント／コメントのみ）の一括設定を行う画面。  
* **【運営】管理画面共通のオーディション切替ヘッダー＆誤操作防止警告**：すべての運営・管理画面の上部ヘッダーに「現在操作中のオーディション名」と進行ステータス（バンド募集中 / 募集締切・調整中 / 採点受付中 / 採点終了・集計）を常時明示するドロップダウン切替UIを配置。ドロップダウンには開催日を表示し、開催日が新しい順（降順）で並べ替えて表示する。直近ではない過去のオーディションや「採点終了・集計」済みの回を選択・操作している場合は、画面上部に警告バナー（例：「⚠️ 過去のオーディションデータを操作中です」）を常時表示し、誤編集・誤更新を防止する。  
* **【運営】部員マスタ・権限管理画面**：部員の一覧表示、CSV/テキストによる一括登録、および個別・一括でのロール変更（ADMIN / VOTER の切り替え）を行う画面。

# **9\. エッジケース・例外処理（Edge Cases）**

* **複数バンド掛け持ちユーザー**：BandMembersテーブルで多対多の関係を保持し、所属するすべてのバンドに対する採点を正確に除外。  
* **通信切断・遅延**：採点データのローカル保存および通信復旧時の自動再送信処理。  
* **同点（タイ）発生時のハンドリング**：ペナルティ前の素点比較、または特定項目（技術点優先など）によるソート仕様の設定。  
* **直前のメンバー変更・バンド脱退への対応**：オーディション直前のメンバー追加・脱退が発生した場合、管理者画面から BandMembers テーブルを即座に更新可能とし、更新後の次回リクエストまたは画面再読み込み時にリアルタイムで自バンド除外判定へ反映。  
* **ステータス連動によるバンド登録編集権限の自動ロック**：オーディションが「募集締切・調整中（`ENTRY_CLOSED`）」以降へ移行した時点で一般部員（VOTER）からの追加・編集権限を自動ロックし、以降の修正は運営管理者（ADMIN）のみに制限。なお、管理者による CSV/テキスト一括登録機能も併存し使い分け可能とする。  
* **サーバーサイドでの権限・バリデーションの二重担保**：フロントエンドでの自バンド非活性/非表示処理に加え、API（Hono）側でもリクエスト送信者の ID と BandMembers および AuditionVoters を照合し、自バンドへの採点リクエストや権限外の操作をサーバーサイドで確実に拒否。  
* **締切直前の同時アクセス・二重送信の防止**：採点締め切り直前のアクセス集中に耐えうるサーバーレス構成（Cloudflare Workers/D1）を採用し、DBレベルの (audition\_id, band\_id, evaluator\_user\_id) 複合ユニーク制約およびフロントエンドの送信中ボタン非活性化により二重送信を完全防止。  
* **学外者および未登録者のアクセス遮断**：Google OAuth 認証時の組織ドメイン制限に加え、部員マスタ（Users/AuditionVoters）に存在しないユーザーからのアクセスに対してはエラー画面を表示し、採点権限およびデータ閲覧を完全に遮断。
